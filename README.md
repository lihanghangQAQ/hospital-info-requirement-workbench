## 三、数据模型（v2 单一数据源）

**单表 `requirements`**（`localStorage` key：`v2_requirements`），用字段 `type` 区分两类需求：

| type | 含义 | 差异字段 |
|---|---|---|
| `RQ` | 信息需求 | `systems` 业务系统 |
| `DS` | 数据统计 | `submitter` 提交人、`risk` 安全风险（含「敏感」）|

**统一字段**：`code` 编号 · `year` 年度 · `priority` 优先级(高/中/低) · `category` 类别 · `dept` 提交部门 ·
`status` 状态(待办/进行中/已完成/已关闭) · `phase` 阶段(需求受理/开发/上线/运维优化) ·
`submitDate`/`planDate`/`doneDate` 三日期 · `crossYear` 跨年长尾 · `desc` 问题描述 · `plan` 处理方案 · `remark` 备注

**计算字段（读取时派生，禁止手填）**：
- `overdue` 逾期：状态为 待办/进行中 且 `planDate < 今天`
- `elapsedDays` 历时：完成日期 − 提交日期（未完成用今天）
- `dueInDays` 距计划交付天数

**P2 新增表**：
- `weekly` 周报归档：每条 `{id,key,label,start,end,year,week,by,createdAt,stats}`（`stats` 含 submitted/done/inProgress/overdue/byCat）
- `annual` 年度总结归档：每条 `{id,year,by,createdAt,stats}`（`stats` 含 total/done/rate/overdue/crossYear/sensitive/avgElapsed/byStatus/byCat/byType）
- `vocab` 受控词表：每条 `{id,cat,term,desc,createdAt}`，`cat ∈ 科室/类别/风险/其他`；首次打开自动种子（信息科/医务部/护理部…、系统优化/表单与病历…）

**localStorage key 一览**（前缀 `v2_`）：`requirements` / `users` / `logs` / `weekly` / `annual` / `vocab` / `settings` / `seeded`。

### 从 v1 自动迁移
旧 v1 数据（`wb_hirw_req` / `wb_hirw_stat` / `wb_hirw_users`）在首次打开时由 `migrateOldData()` 自动并入 `v2_*`，
`req`→`RQ`、`stat`→`DS`（安全风险「敏感」→`sensitive=true`），用户角色「管理员」→`admin`。**原数据不丢。**

## 十、已修复的关键问题（记录）

- `doImport` 原用 `K["requirements"]` 取存储键失败（`K` 键为 `req`），导致从 JSON 恢复写入 `undefined` 键、恢复失效；已改为显式键名映射。
- P2 注入时主干 change 处理器写的是 `G.anaYear`（非 `anYear`），P2 年度视图初版误用 `G.anYear` 导致下拉切换不刷新；已统一为 `G.anaYear` 并复用主干 `#anaYear` 选择器。
- 注入采用「归一化 CRLF→LF + 括号/锚点断言 + 已注入守卫」避免中文注释/换行/缩进导致的锚点失配与重复注入。

## 十三、云端同步（Supabase）+ GitHub Pages 部署

### 架构
- **纯静态**：无框架、无构建、无 npm。仓库根目录 `index.html` + `assets/*.js`，Pages 直接托管 `main` 分支根目录。
- **无 SDK**：不使用 Supabase 官方 JS SDK（国内 CDN 不可靠），改用原生 `fetch` 自写最小客户端 `assets/sb-client.js`。
- **分层**：`assets/config.js`（连接配置）→ `sb-client.js`（REST 客户端）→ `sb-sync.js`（登录 / 同步 / 登出）。
- **无侵入接入**：`sb-sync.js` 在主脚本之后加载，只覆盖 `doLogin` / `logoutApp` / `enterApp` 三个入口并包装 `saveArr`，主业务逻辑零改动。

### 数据表与 RLS
6 张业务表：`requirements` / `app_users` / `logs` / `weekly_archives` / `annual_archives` / `vocabularies`。
- 主键 `id uuid`（与前端 `uid()` 生成的 UUID v4 完全一致）
- `user_id uuid` 外键 → `auth.users(id)`，级联删除
- **全部开启 RLS**，读写策略统一 `auth.uid() = user_id`
- 建表 SQL：`supabase/schema.sql`（可重复执行）

### 同步策略
- **本地优先**：修改先落 localStorage，再异步推云端，离线可用。
- **幂等写**：推送一律 `upsert`（`Prefer: resolution=merge-duplicates`），按 id 合并，重复执行不产生重复行。
- **差集删除**：以上次已知云端 ID 集合与本地 ID 集合做差集，删除本地已不存在的行。
- **并发控制**：debounce 800ms 合并 + Promise 串行队列，杜绝并发重复保存；失败指数退避重试 3 次。
- **冲突判定**：以 `modified_at` 做最后写入胜出（last-write-wins）。
- **首登判定**：云端无任何数据时保留本地示例数据并上推；否则以云端为准、丢弃本设备孤立行，避免多设备重复示例数据。

### 登录 / 登出
- 邮箱 + 密码登录，token 持久化到 localStorage，**刷新自动恢复登录态**。
- token **提前 60s** 判定过期；请求遇 401 自动用 refresh_token 续期并**只重试一次**；仅当 refresh 本身失效才清空会话。
- **登出**：撤销远端 refresh_token → 清 `hirw_sb_session` → 清全部 `v2_*` 业务键 → 重置全局状态（含 `G.user` / `logs`）→ 清空主区域并回到登录页（未登录空数据态），保证账号间完全隔离。
